# 正式 Maa 流程使用解码读取

正式 Maa 工作进程已将库存、订单和农场员工计划的数据读取切为本地解码。
本次只完成代码接入、模拟回归测试和实际只读数据验证，**没有启动交单、保存计划、领取或刷新订单**。
操作后的游戏反馈和缓存写入时机尚未实机验证。

## 接入范围

| 入口 | 替换的业务读取 | 保留的原逻辑 |
| --- | --- | --- |
| 普通、聚会、外卖订单 | 材料 ID/名称、单次需求、玩家库存、缺口、菜单解锁与等级 | 打开页签、选择卡片、完成次数勾选、接受及领奖的 UI 定位与点击 |
| 一号位品类检查 | 完整材料名称和菜品等级条件 | 选中状态、换单/加速按钮及原白名单规则 |
| 背包与饲料循环库存 | 玩家背包产品数、饲料物品 19 的数量 | 其他页面导航与操作方式 |
| 员工空闲检查、保存后核对 | 指定岗位的完整计划目标、员工持有产品、重复设置 | 原员工能力表、作物图标定位、选择/加号/保存的坐标和点击方式 |
| 员工计划监控 | 各产品累计与员工持有量、计划分母、计划是否清空 | 原领取按钮定位、领取点击及农场导航 |

界面选中高亮、页签、按钮、勾选状态等仍通过原 UI 识别确认，不用缓存猜测当前选中了哪张卡。
聚会/外卖的实际完成次数仍读取原界面控制数，材料为解码的单次数量乘以该次数。
磨坊独立机器的补货时长、生产设置及机器产物计数保留原流程，它们不属于本次的农场员工计划目标读取。

## Maa 默认启用

`agent/cycle_bridge.py` 给工作进程设置 `CARROT_STATE_READER=decoded`；
`tools/ui_worker.py` 在导入业务步骤前也强制设置同一值。
短循环和日常调度后续启动的子进程继承它，因此实际操作步骤调用的是新读取后端，
不是仅在数据窗口或预览中显示新数据。

多数独立 CLI 未通过 Maa 工作进程启动时仍默认识图，便于离线识图测试。
监控收取（`monitor_employee_products.py --apply`，含普通订单循环等调用）例外：未设置 `CARROT_STATE_READER` 时使用解码，配方冲突且岗位仍持有产物会记为 `recipe_conflict_skip` 并跳过该岗位。只有显式 `CARROT_STATE_READER=ocr` 才改回识图轮询，此时不会做该跳过。
本次没有改动 Maa 的点击封装、前台保护、鼠标/键盘输入方式或原生产任务的执行开关。

## 后端与一致性检查

新增 `tools/decoded_runtime.py`，只处理数据，不导入游戏控制器或 OCR。
它运行 `read_only_game_state.cjs automation`，一次快照同时返回库存、订单、员工计划，
不读取狮王任务堆内存，不要求家族任务板已打开。

- 每次读取检查结构和采集时间；解码失败直接报错，不读磁盘旧输出代替，也不静默退回 OCR。
- 订单必须显式指定类型、槽位和实际完成次数，不能从旧的当前选中项推测。
- 首次读取记住订单 UID，接受前再次核对 UID、完整配方及库存；变化时停止。
- 非待接取状态直接停止，不把配送/已完成状态误当作需要更换的不可读配方。
- 菜单等级规则来自本地配置和菜单记录，保留普通简单订单的客户端例外规则。
- 员工进度按 `g_items + col_m` 中对应计划产品的数量计算；不把玩家背包计入员工进度。
  每种产品分别达到目标才算完成，一种产品超产不能抵消另一种的缺货。
- 监控领取前核对当前解码计划与已保存的分配记录，不能仅凭相同总数量领取别的计划。
- 空闲检查同时要求没有计划目标、员工持有产品和生产操作；缺少岗位/员工记录时停止。
- 普通单排产拒绝没有 `state_reader: decoded` 的旧 OCR 订单检查点，避免旧数据混入。

员工缓存的 `ae_items` / `g_items` 是连续的 `ID_数量_ID_数量` 配对列表，
已修正多作物解析，保留零值；`col_m` 等映射仍按 `#` 分隔读取。

## 未保存草稿的边界

工作计划编辑器中尚未保存的加号数量不在 MMKV 中。
新路径保留原来的作物选择、加号和保存点击，不把点击次数伪装成“已读回”。
保存后才通过解码核对完整产品及数量和重复设置，等待最多约 8 秒；
未得到一致结果就停止，不自动重复保存或继续领取。

[首轮记录](DECODED_LIVE_ACCEPTANCE_2026-10-18.md)。
随后修复领取与弹窗处理，已完成一张勾选6次的真实聚会订单，保存、领取、扣料更新及订单领奖均确认，
详见[六次实机验收记录](DECODED_SIX_LIVE_ACCEPTANCE_2026-10-18.md)。
正式默认选单不再自动取消6次批量勾选；实际次数不足6时停止。

## 操作后的确认和弹窗

正式解码路径的领取不再以鼠标调用成功作为到账证明。解码读取完成后，
重新定位目标岗位的收获按钮，在两张稳定画面上确认实际按钮中心，再点击一次。
随后最多等待约8秒，同时核对该岗位计划和待领产品清空、对应产品进入背包；
没有得到一致结果就抛出 `CollectionUnconfirmedError`，不自动重领或清计划。

交单后使用同一后端核对订单进入进行中/成功状态，以及各材料精确扣除所选次数的用量。
厨师缺失提示必须同时匹配正文与“继续订单”按钮，才沿用原点击方法确认一次；
不会选择“前往”获取员工。打烊提示必须匹配“餐厅打烊”“等天亮”的正文，
不能只识别厨师和打烊弹窗共有的“提示”标题。
打烊时关闭提示并停止，不将其计为交单成功，也不自动再次接受。
未知提示或约12秒内未确认状态与扣料时停止，不自动重发接受点击。

批量交单在实际点击接受前再次核对勾选状态和完成次数。
员工尚未达标时仅检查缓存进度，保持在农场等待；达标后才打开员工页领取，
减少旧识图轮询反复开关页面导致的暂停生产和滚动位置变化。

领奖先处理正文为“订单解锁历史新高”的新高奖励弹窗；普通领奖按钮被弹窗遮暗时，
即使模板分数足够也不点击。结算恢复沿用已接受检查点，只领取奖励，不再次发送接受。

相关回归检查：`tests/test_decoded_action_confirmation.py`。

## 只读验证

无需打开任何 Maa 生产任务，可直接验证同一个正式读取后端：

```powershell
.venv/Scripts/python.exe -X utf8 tools/validate_decoded_runtime.py
```

这个入口不导入 Maa 控制器，不启动业务流程，仅执行只读解码和计算，结果写入：

- `.tmp/decoded_runtime/snapshot.json`：新后端的实际快照。
- `.tmp/decoded_runtime/validation.json`：按 3/6 次口径转换的订单、员工目标和进度。

本次实际读到 24 种库存、27 条订单、9 个员工计划，映射缺失为 0。
其中 21 条订单可进入现有配方流程，2 条因菜单未解锁/等级条件被阻止，
4 条不符合原流程的 2–4 种材料规则；这些业务规则没有扩大。
报告明确记录 `game_operations_executed: 0`、`formal_action_chain_executed: false`。

回归测试中的所有业务点击和游戏控制器均被替身拦截；测试包括不调用旧材料 OCR、
不连接游戏的背包读取、UID 变化/旧快照/旧 OCR 检查点拒绝、完整多作物解析、
保存后未确认不报成功及不重复保存，以及 Maa 分派前强制启用解码。

```powershell
.venv/Scripts/python.exe -X utf8 -m unittest discover -s tests -p test_formal_decoded_runtime.py -v
node --test tools/read_only_game_state.test.cjs
```
