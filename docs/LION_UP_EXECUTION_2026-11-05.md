# 本人苹果UP执行与验收

日期：2026-11-05，Asia/Singapore。0.15.0，分支`codex/lion-up-completion`。

## 范围

从本人已接、已升级的苹果收获UP开始，指定员工在农场上阵即可，生产人员不必是指定员工。用户本轮选择员工排产；先选择自然生产，后明确由用户手动催熟，催熟后通知脚本接续收取。脚本不使用肥料、不购买次数、不放弃或接取新任务，不覆盖其他岗位计划。

新界面“自动运行设置”中的“本人已接苹果UP（一任务）”可实际开始、暂停／继续、结束。只绑定一个任务；任务变更、身份变更、期限结束或未知条件明确停止，不自动换任务。整期26次、接取／升级／换人及其他UP不在此版本启用。

## 关键实现

- `lion_task_operation.py`：绑定账户／家族／期数／槽位UID／任务实例UID；新快照核对状态、进度、上阵与期限。个人状态2且进度达到目标才可领奖，库存及产量不代替任务进度。
- `run_lion_task.py`：复用员工保存、监控和单次收取模块，狮王生产有独立canonical记录。每批后按任务实际缺口重算，使用当前员工界面容量，在空闲岗位间分配。已存岗位只回读，不重进编辑或保存；人工已使任务完成时直接验证领奖，余下在产和未决记录保留。
- `lion_task_ui.py`：现有Maa后台截图、OCR、窗口消息输入；仅已识别手机／家族／任务板及明确领取按钮可点击。领奖持久化意图先于唯一领取点击，异常／退出后只补证，不重发。
- 领奖确认：原个人任务消失或GAINED，3956余额恰减1、铃铛恰增82、5740恰增1，账户／期数不变；之后已知页面导航返回农场才标记completed。领取结果已确认而返回失败，单独恢复返回。

## 动态数量和包100规则

本地包100抽取的ViewFarmModel（27248字符，SHA256 `d4d6bc279da9bea0fc8e06024602fe1516a94a32142a8a4a491eea9084ab4e3c`）和EnumTypes与98逐字节一致。静态原始片段与对照摘要只保留本地。REA对生产抽取图的覆盖为partial（拼接模块不能独立解析），不据此宣称动态语义已验证；上述相同比较是独立的原文字节比较。狮王完成回调的独立静态分析未执行游戏代码。

客户端`getFieldCropDatasList`会按当前载体数量补足尾部槽位并初始化为零。包100读取器将这些新增尾部槽位标注`raw.clientInitializedTuple=[0,0,0,0]`，原始datasList仍为null；不是把任意损坏或未知元组当空。现有损坏元组、数据超出当前数量和未核对包仍阻塞。建筑树位数量随当前缓存变化，不写死11／13／16；目标区域完整性独立核对。其他包原缺数据守卫保持。

员工容量与土地数量分开：当前果园2计划界面容量50，旧能力表为46。本版本狮王路径实际读取容量并在保存前重核，不把旧值强行用于当前员工；正常订单旧分配器仍保留原有能力策略，本轮没有整体重写。

## 实机记录与断点

开始时本人任务要求204个苹果，当前66/204，指定员工已在果园2上阵，期限有效；两果园原计划空，果园2缓存有两个新槽未落盘。旧普通订单员工操作经已有守卫核对同一员工、计划已清空且无收取日志后，保存证据归档为superseded_plan_cleared；没有删除旧记录或重复收取。

首批果园1保存苹果50并回读。扩建规则核实后补入果园2，原果园1不重存。果园2请求50，但实际保存回读为39，原守卫停止且没有重发保存。修复只对可证明的较小同品类保存结果：两份新读取一致、员工身份不变、重复关闭、无收取意图；原请求、较小实际值及快照保存为partial_save证据，再按实际39接续。其他配方／更大数量／有收取历史／身份变更不走该路径。新增保存前草稿数量确认与可观测缺口补齐，防止把发送加号次数当实际数量。

用户手动催熟后通知尚未收取。新读取果园1持有苹果50、果园2计划39而实际持有苹果40，任务进度仍66。正式新界面运行冻结请求启动，按实际持有量收取并回读任务，额外苹果不得隐藏任务缺口或重复计算。实际后续结果以本节更新和canonical记录为准，尚未完成时不能宣称领奖成功。

本地canonical：`.tmp/lion_tasks/active.json`，具体任务目录内`task.json`、`production/active.json`及各批assignment／saves／claims。新界面运行记录在`.tmp/hud_runs/`；原始实机、静态包、截图与测试日志在`.tmp/lion_up_completion_2026-11-05/`。以上不上传。
